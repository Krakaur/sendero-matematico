# Servicio docente: Workers/D1 y receptor local

Actualización del 14 de octubre de 2026: el receptor de nube está desplegado en `https://sendero-aula.dirkhans.workers.dev`, con una API 3 adaptada a D1, consultas incrementales y copias cifradas por fragmentos. Leer `CLOUDFLARE.md` para el estado de publicación y operación. Los apartados siguientes describen el receptor Node/API 2 y la evaluación que precedió a la migración; sus referencias a alojamiento pendiente son históricas. No se requiere ejecutar Node localmente para usar el receptor de nube. La web 0.10.0 está publicada y sus 52 archivos coinciden con el contenido de Git.

## Receptor Node/API 2 conservado para pruebas locales

El receptor Node 24 utiliza SQLite y claves de invitación separadas para docente y estudiante. La clave de estudiante queda vinculada al identificador del primer informe aceptado. El servidor confirma los identificadores de sesiones recibidas, deduplica reintentos idénticos y rechaza cambios incompatibles en una sesión ya recibida. Cada clave docente accede solamente a su aula. Las tareas del aula indican contenido y título; orientan práctica adaptativa, no acreditan cumplimiento curricular o una evaluación supervisada.

La web guarda la lista de confirmaciones y reintenta al terminar una aventura, al recuperar conexión y cada minuto mientras la aplicación permanece abierta y visible. Un navegador cerrado no ejecuta esos reintentos. Desvincular la invitación detiene nuevos envíos; no elimina lo ya recibido. El receptor no recibe alias ni contraseñas locales. Sí recibe identificadores, fechas y respuestas, que constituyen registros vinculables, no anónimos.

## Prueba local y puesta en marcha

Requiere Node 24 con `node:sqlite`. `node server/cli.mjs` abre el receptor en 127.0.0.1:4180. El directorio de datos predeterminado es `server/private`, excluido de Git. Se puede sustituir mediante `SENDERO_DATA`. Con `SENDERO_ENDPOINT` definido, `node server/cli.mjs create-class "Nombre del grupo"` crea un aula y guarda una invitación docente y ocho invitaciones individuales en el directorio privado. Una invitación estudiantil es para un solo perfil, no para compartir entre toda la clase. No publicar esos archivos ni incorporarlos a una captura o informe público.

La persona adulta importa la invitación en «Docentes → Vincular con un aula» y confirma el servidor de destino. El tipo de invitación debe coincidir con el perfil local. En el servicio de producción se define `SENDERO_ORIGINS` con los orígenes web autorizados; la edición Windows requiere valorar y permitir explícitamente el origen `null` de archivos empaquetados. El ejecutable permite únicamente solicitudes HTTPS del tipo usado por la aplicación; mantiene bloqueados scripts y navegación externa.

Producción requiere administrador, dominio HTTPS, proxy inverso, almacenamiento persistente, copias protegidas y procedimiento de revocación. No existe un receptor público desplegado. GitHub Pages no ejecuta este servidor: [documentación oficial](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). La API SQLite utilizada está descrita en [Node 24](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html).

La web 0.9.0 incorpora una interfaz docente para emitir invitaciones individuales y revocarlas, con un máximo de 60 invitaciones estudiantiles por aula. La revocación conserva los informes recibidos y elimina la copia remota cifrada asociada. Siguen pendientes rotación de claves, recuperación administrativa de acceso, borrado trazable de expedientes, paginación y pruebas de carga/abuso. La posesión de una invitación autentica el permiso técnico, no la identidad civil ni la condición profesional de docente.

## Proyectos y copia remota en la API 2

`GET /capabilities` anuncia `projects`, `vault` y `students`. La entrega de proyectos es opcional: el estudiante debe activar el envío de construcciones, revisiones y notas. `POST /projects` valida la estructura y las condiciones matemáticas; confirma IDs y rechaza modificaciones incompatibles de un proyecto recibido. `GET /projects` requiere permiso docente del aula. Esta validación no verifica autoría, ayuda externa ni explicación oral.

`POST /vault` conserva un respaldo AES-256-GCM producido en el navegador; la contraseña no viaja al servidor. Cada invitación queda vinculada a un perfil. La revisión esperada se comprueba dentro de una transacción y una copia obsoleta obtiene conflicto 409. `GET /vault` permite recuperar la copia con la misma invitación y su contraseña, elegir una contraseña local nueva y conservar la construcción pendiente. Son guardado y recuperación explícitos: no hay sincronización automática, cuentas con correo ni fusión de cambios concurrentes. Perder la contraseña del respaldo impide descifrarlo.

El despliegue requiere elegir un servidor que ejecute Node 24 y permita almacenamiento persistente, un destino HTTPS y una persona responsable. No se ha elegido proveedor ni adquirido un plan. Para prepararlo se utiliza el mismo `server/cli.mjs`, con `SENDERO_DATA` fuera del árbol publicado, `SENDERO_ENDPOINT` igual al destino HTTPS y `SENDERO_ORIGINS=https://krakaur.github.io`. El proceso escucha únicamente en loopback y debe quedar detrás del proxy HTTPS del alojamiento. No incluir invitaciones, base SQLite o copias en `gh-pages`. Antes de un uso escolar real deben establecerse conservación, respaldo, revocación y administración de datos del centro; la API local no reemplaza esas decisiones.

Para repetir el recorrido sintético de interfaz, abrir `web/` en `http://127.0.0.1:8768`, ejecutar `node scripts/qa-classroom-server.mjs` y usar `scripts/qa-web-cloud-ui.js` con Playwright CLI. El servidor de prueba usa memoria, claves ficticias conocidas y solo loopback en el puerto 4180 permitido por la política de contenido local. Nunca se publica como servicio. Los contextos de navegador representan instalaciones separadas en un mismo equipo, no dos teléfonos físicos.

## Control de consumo y alojamiento

Condición expresa del autor, 14 de octubre de 2026: el servicio debe detener o rechazar operaciones al alcanzar sus límites, sin convertir el exceso en cargos. Cada prueba remota debe incluir comprobaciones de consumo. El alcance inicial es uso privado de desarrollo; no presupone difusión pública ni autoriza un plan de pago.

La revisión autenticada de esa fecha confirmó Workers Free activo y ngrok Free. El receptor continúa siendo Node 24/SQLite local: no existe todavía una adaptación a Workers/D1 ni un despliegue de ese backend. La web de GitHub Pages ejecuta el juego en el navegador. Sin una invitación de aula vinculada, una partida individual no invoca el receptor docente. El multijugador actual utiliza PeerJS/WebRTC y servicios de señalización ajenos a Workers; sus cuotas deben evaluarse por separado.

Workers Free incluye 100.000 solicitudes por cuenta y día, con reinicio a las 00:00 UTC, y 10 ms de CPU por petición HTTP. CPU significa ejecución efectiva; la espera de red no es CPU y los minutos de una partida no se convierten directamente en minutos de Worker. El exceso diario produce error 1027 y el exceso de CPU puede terminar la invocación con 1102. Si se configura una ruta sobre otro servidor, deberá usar `fail closed` para evitar que un agotamiento eluda el Worker. No existe todavía esa ruta de Sendero. Véanse los [límites de Workers](https://developers.cloudflare.com/workers/platform/limits/).

Workers no aplica un cargo separado por transferencia de salida; esto no constituye una garantía de velocidad de red. El plan Paid tiene cuota base y consumos adicionales, por lo que no satisface por sí solo la condición de coste variable cero. Mantener Free y no activar productos adicionales con facturación por uso. Una alerta de presupuesto o un límite de CPU por petición no reemplaza un corte de gasto agregado. La renovación del dominio es un concepto independiente. Fuente: [precios de Workers](https://developers.cloudflare.com/workers/platform/pricing/).

D1 Free permite 5 millones de filas leídas y 100.000 escritas al día; al agotar esas cuotas rechaza consultas. El almacenamiento máximo es 500 MB por base y 5 GB por cuenta. Las filas leídas incluyen las examinadas por la consulta; los índices también pueden añadir escrituras. Medir `meta.rows_read`, `meta.rows_written` y almacenamiento, no solamente el número de consultas o de partidas. Fuentes: [precios de D1](https://developers.cloudflare.com/d1/platform/pricing/) y [límites de D1](https://developers.cloudflare.com/d1/platform/limits/).

ngrok y Cloudflare Tunnel publican servicios que se ejecutan en otra máquina. Los Cloud Endpoints de ngrok gestionan tráfico y políticas, pero no constituyen un alojamiento equivalente al receptor programable de Workers con D1. La URL de desarrollo de ngrok no demuestra contratación de CPU, disco o una base de datos. ngrok Free incluye 1 GB de salida y 20.000 solicitudes HTTP mensuales; no pasar a Pay-as-you-go para continuar una prueba agotada. Fuentes: [agentes de ngrok](https://ngrok.com/docs/gateway/agent), [Cloud Endpoints](https://ngrok.com/docs/gateway/endpoints/cloud-endpoints), [límites gratuitos](https://ngrok.com/docs/pricing-limits/free-plan-limits) y [planes](https://ngrok.com/pricing).

Antes de cada prueba remota se debe registrar fecha UTC, versión, proveedor, cuenta mediante identificador no secreto, plan activo, servicios habilitados, consumo inicial y saldo disponible. Definir participantes, duración máxima, solicitudes máximas y operaciones de base de datos previstas antes de iniciar. Preferir simulación local; un ensayo remoto requiere datos sintéticos y un presupuesto acotado. Si no puede verificarse el plan o el consumo, continuar únicamente en local.

Durante la prueba se deben contar peticiones reales —incluidos preflight CORS, reintentos y sincronizaciones en segundo plano— y revisar métricas al terminar cada escenario. Todo generador automatizado debe tener un límite de peticiones y duración que detenga la prueba; no ejecutar carga remota ilimitada. Registrar CPU observada y errores cuando exista el Worker, además de filas leídas/escritas y bytes cuando exista D1. Detener los ensayos ante agotamiento, errores reiterados o crecimiento inesperado; no habilitar un plan superior como recuperación automática. Las métricas del proveedor pueden retrasarse y no deben ser el único mecanismo de corte.

Después de cada prueba se registran consumo final, diferencia, resultado y margen restante en `qa-private/consumo-hosting/`, sin tokens, invitaciones ni expedientes. Cuando la ventana cruza un reinicio de cuota, separar los intervalos. Los contadores de cuenta pueden incluir otros proyectos; una diferencia no demuestra por sí sola consumo exclusivo de Sendero. La incorporación futura del backend deberá reducir consultas redundantes y contener los reintentos ante agotamiento, conservando el progreso local. Estos controles de aplicación y de ejecución de pruebas aún requieren implementación y validación; este apartado establece la condición de aceptación.

La capacidad de partidas en Workers no está medida. Para solicitudes, el techo teórico es `floor((100000 - solicitudes_ya_usadas - reserva) / solicitudes_por_participación)`, sujeto además a CPU, D1 y concurrencia. La sincronización actual consulta tareas y capacidades cada minuto con la pestaña visible y el aula vinculada, más envíos de informes/proyectos y consultas docentes. El ensayo local siguiente aporta recuentos para escenarios explícitos, sin certificar la capacidad del proveedor. No extrapolar esta fórmula a un servidor multijugador continuo.

## Medición local del 14 de octubre de 2026

`node scripts/qa-backend-consumption.mjs` ejecutó 5.015 solicitudes HTTP exclusivamente sobre loopback, con Node 24.16.0 y SQLite en disco en un Intel Core i3-9100. El servidor se ejecutó en un proceso hijo separado del cliente; se midieron diferencias de `process.cpuUsage()` en tres lotes por operación, excluyendo el calentamiento. Estado PASS. Registro: `qa-private/consumo-hosting/local-2026-10-14T18-48-38-948Z/measurement.json`, con hashes de fuentes, entorno, muestras y límites metodológicos. No se usaron recursos de Cloudflare ni datos reales.

La reproducción del módulo real `exchangeClassroom` incluyó sincronización al entrar, una por cada minuto simulado y otra al completar la sesión. Una partida estudiantil de 5, 15 o 60 minutos produjo respectivamente 15, 35 o 125 peticiones de aplicación. Sin aula vinculada, el módulo produjo cero peticiones al backend. El tiempo se simuló; no fueron partidas jugadas durante esos intervalos ni recorridos de interfaz. El panel docente abierto 15 minutos produjo 80 peticiones, contabilizadas por separado. No se incluyeron reintentos, sincronizaciones manuales, proyectos ni copias remotas.

Un escenario conservador añade una petición OPTIONS por cada petición de aplicación: 30, 70 o 250 peticiones HTTP para esas tres duraciones. Esto modela preflight CORS sin aprovechar caché; no es una medición de un navegador. El caso de 15 minutos representa 0,07 % de 100.000 solicitudes y un techo aritmético de 1.428 participaciones diarias si esa fuera la única restricción y no existiera otro consumo. No es una garantía de concurrencia, CPU ni cuotas D1.

Las medias de CPU del proceso servidor fueron 0,30 ms para consultar tareas, 0,17 ms para capacidades, 0,08 ms para OPTIONS y 2,19 ms para almacenar una nueva sesión de ocho respuestas. La composición de estas medias para el escenario de 15 minutos, incluidos 35 preflights, da aproximadamente 13 ms de CPU local acumulada, repartida entre 70 peticiones. Es una estimación derivada, no CPU medida en Cloudflare ni una medida directa de una partida completa. La contabilidad de CPU del sistema operativo tiene granularidad; se conservan los lotes y no se calculan percentiles de CPU por petición a partir de ellos.

La consulta docente de historial completo pasó de una media local de 0,26 ms con una sesión a 6,33 ms con 300 y 28,90 ms con 1.500; el último caso devolvió aproximadamente 2,77 MB de JSON. Antes de migrar, paginar o consultar cambios incrementales y limitar tamaños; no resolver el crecimiento enviando todo el historial cada minuto. Las medidas son secuenciales y no prueban arranque en frío, concurrencia, WebRTC, copias grandes ni una carga escolar real.

Para probar la futura adaptación a Workers sin desplegarla, Cloudflare permite ejecutar `workerd` mediante Wrangler/Miniflare con recursos simulados locales. Mantener las vinculaciones remotas desactivadas. Las cifras de CPU del receptor Node/SQLite no certifican el límite de 10 ms de Workers; después de adaptar y validar localmente, una prueba remota acotada debe confirmar CPU y filas D1 antes de aceptar la capacidad. Fuente: [desarrollo local de Workers](https://developers.cloudflare.com/workers/local-development/).

## Dimensionamiento local de almacenamiento

El 14 de octubre de 2026, `node scripts/qa-storage-footprint.mjs` midió 52 archivos en `web/`, con 7.921.715 bytes (7,92 MB decimales). La referencia local `origin/gh-pages` contiene 7.913.374 bytes en 52 archivos; no se volvió a descargar la publicación en esta medición. El banco principal ocupa 2,96 MB y las dos ilustraciones mayores suman 4,19 MB. Estos archivos públicos pueden permanecer en GitHub Pages, cuyo límite de sitio publicado es 1 GB. Fuente: [límites de GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).

Se midieron 16 sesiones aritméticas válidas de ocho respuestas, entre 1.855 y 1.942 bytes de JSON, y 16 recorridos completos de ocho actividades de construcción, entre 1.846 y 1.874 bytes. Son casos sintéticos resueltos correctamente, sin notas extensas ni historial de errores: no son máximos del formato. Con el esquema SQLite actual e índices, el almacenamiento asignado fue 0,262 MB para 100 registros, 2,191 MB para 1.000 y 21,524 MB para 10.000. La medición incluye 45.056 bytes de estructura inicial; no representa facturación D1, archivos WAL, réplicas ni validación funcional de un perfil de 10.000 sesiones.

Las copias cifradas reales producidas por `encryptBackup` ocuparon 0,252 MB con 100 sesiones, 1,260 MB con 500 y 2,520 MB con 1.000. Una copia remota duplica parte del historial ya recibido por el aula. Como presupuesto orientativo, 1.000 registros más una copia de ese historial suman unos 4,7 MB; 10.000 registros repartidos entre diez perfiles de 1.000 y una copia por perfil serían del orden de 47 MB, antes de otros datos y margen. Errores, notas, banco de razonamiento, archivos adjuntos futuros y política de conservación pueden alterar estas cifras.

El límite de 500 MB por base D1 Free parece suficiente para pruebas privadas de este tamaño. Sin embargo, D1 limita cada fila a 2.000.000 de bytes: la copia sintética de 1.000 sesiones ya supera ese límite. El receptor Node actual guarda la envoltura en una sola fila; antes de trasladarlo a D1 debe dividir copias en fragmentos o establecer un límite compatible, preservando revisión e integridad. Disponer de espacio total no evita este requisito.

GitHub Pages sirve los archivos públicos y el navegador conserva progreso local; esos mecanismos no sustituyen una base privada compartida entre dispositivos. No publicar invitaciones, expedientes o copias de estudiantes en el sitio estático. Cloudflare Pages también sirve archivos estáticos (20.000 archivos en Free, hasta 25 MiB por archivo), pero las Functions cuentan contra Workers y la persistencia requiere almacenamiento separado. R2 tiene una franquicia de 10 GB-mes para almacenamiento Standard con cobro de excedentes; no es necesario activarlo para este alcance ni debe confundirse con un corte gratuito garantizado. Fuentes: [Pages](https://developers.cloudflare.com/pages/platform/limits/), [Functions](https://developers.cloudflare.com/pages/functions/pricing/) y [R2](https://developers.cloudflare.com/r2/pricing/).

Medición enteramente local, sin HTTP, credenciales ni consumo Cloudflare. No implica que Workers/D1 estén desplegados ni que la fragmentación de copias esté implementada.
